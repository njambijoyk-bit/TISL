A private brain for Mimi

Today Mimi sends each question, plus a slice of store data, to an outside AI. This guide designs the layer that should come first: a local, role-aware brain that answers from our own structured knowledge and our own database, on our own server, and only asks Gemini, Claude or OpenAI when we have said it may.

  • Design: complete draft
  • Prototype: runs in this page, no network
  • Server code: not built yet
  • 9 Oct 2026 · code read at commit e15e726

Ask it something → What's wrong with today's flow?

1The short version

🏠

Answer locally first

Where's my order, how do I pay, what does clearance 3 mean: these have known answers in our own knowledge or our own database. No outside AI needed, no tokens spent, and it still works when a provider is down.

🔐

Role-aware by construction

Every knowledge entry and every data lookup names the permission it needs. The caller's permissions are applied before matching, so a restricted entry can't be scored, quoted or leaked.

🧱

Structured HTML now, NLP later

Knowledge is written as plain <article class="kb"> entries. A transparent matcher answers from them today. Every logged question becomes the labelled data we train the NLP on later.

🚪

The outside AI gets a leash

Gemini, Claude, OpenAI and Qwen stay available through the existing AiGateway, but the owner chooses, per audience: never, public context only, or redacted and scoped.

🧩

Fits what we already built

It reuses hasPermission(), the block, consent and harm services, the Mimi logs and analytics screens, and the "no role names in code" rule. Nothing parallel is invented.

Why now: three things found while reading the current code
  1. Personal data leaves with every message. A customer's name, email, phone, spend, store credit, orders and payments are placed in the prompt that goes to the provider.
  2. Staff lookups skip the permission engine. "Look up order…" and "look up customer…" check only that you can open the admin area, not customers.view, your data scope or your branch limits.
  3. The harm scan runs after the outside call, inside the logger, so a harmful question has already left by the time it is scanned.

Evidence with file and line numbers is in chapter 3. I read the code and tested the two regexes; I have not exercised these paths against a running instance.

3Where Mimi stands today

Mimi already has a lot worth keeping. To design the new layer properly, here is what happens to a message now, read from the code at commit e15e726.

One message, as it is handled now

  1. Arrives at POST /api/chat (signed in, throttled 30 a minute) or POST /api/chat/guest (10 a minute). api.php:111, 386
  2. Session and block check (MimiSessionService, MimiBlockService). Message limited to 2,000 characters, history to 20 turns. ChatController.php:33–57
  3. A prompt is built. Store info, up to 30 products (50 for staff), 30 services, 15 categories. For a customer: name, email, phone, customer number, tier, total spent, store credit, loyalty points, last 8 orders, last 5 payments, 3 projects, promo and referral codes. For staff: stats plus whatever the intent detector finds (an order, a payment, a customer, recent activity). ChatController.php:62–73, 138–335, 344–403
  4. The whole prompt goes to a provider through AiGateway::run('mimi', …), trying the keys in order across Anthropic, OpenAI, Gemini and Qwen and moving on when one fails. ChatController.php:835–870; AiGateway.php:163–186

Consent

Several provider keys, ordered by purpose, with the last error shown on the AI → Keys screen.

5Who is asking? Role awareness

"Role-aware" here does not mean the chatbot knows job titles. It means every decision is made from what the platform's access engine says this person may do, which is how the rest of the platform already works (docs/IDENTITY_AND_ACCESS_PLAN.md).

The caller context

Built once per message, on the server, from the signed-in user (or an anonymous guest). The browser never supplies it.

Six rules that keep it safe

  1. Permissions, never role names. Entries say data-requires="customers.view", not "managers only". This is the platform's own rule (the ESLint no-restricted-syntax rule and NoRoleNamesInCodeTest fail the build on role names in code), so a role you build tomorrow works without a code change.
  2. Filter first, match second. Entries the caller can't see are removed before scoring. A hidden entry can't win, can't be quoted in a suggestion, and can't influence a score.
  3. A refusal never contains the hidden content. Each entry carries its own public "when not allowed" sentence. A record that exists but is outside your scope gets the same reply as one that doesn't exist.
  4. Check twice. The entry-level check is a pre-filter. The resolver that fetches live data checks again at run time, with its own declared permission and scope. If the two ever disagree, the stricter wins.
  5. One path for everyone. There is no "admin mode". The owner holds every permission, so the owner simply sees more entries.
  6. Clearance is not a permission. It decides whom you may manage; it grants nothing. So entries never key on a clearance number.

"Hidden" versus "refused"

If hidden entries were simply invisible, a chef asking "look up customer jo@example.com" would get a confused "I don't know", which is a poor answer and teaches them nothing. So the engine does a second, shadow pass over the entries the person can't see but whose topic their kind of account could reach: the same kind of account missing a permission (a chef and the order lookup), or a guest who could sign in to see an own-account entry. It uses that pass only to decide whether a restricted topic was asked about, and only when that hidden entry is clearly a better match than anything visible. It then replies with that entry's own public sentence ("You don't have the permission to look up customers' orders") and nothing else.

Topics that belong to a different kind of account are not advertised at all. A customer who types a staff question simply hears "that isn't written down yet", and never learns a lookup screen exists.

The trade-off, stated plainly

A person with the right kind of account learns that a topic exists and that they lack access, never any content. That is what the admin menu already reveals by greying items out. If even that is too much for a topic, give its entry no .kb-denied text and the shadow pass will skip it.

6The structured HTML format

This is the "structured HTML before we train an NLP" step. One entry answers one question. It is plain HTML, so it reads well to a person, diffs well in git, and a machine can read it without training anything.

Anatomy of an entry

<!-- chapter 14 holds the live ones; this is the shape -->
<article class="kb" id="staff.order-lookup"
  data-audience="staff"
  data-requires="customers.view"
  data-sensitivity="restricted"
  data-resolver="orders.lookup"
  data-keywords="order voucher invoice sale find lookup"
  data-follow="staff.customer-lookup"
  data-reviewed="2026-10-09">

  <h4 class="kb-title">Look up an order</h4>

  <ul class="kb-q">                       <!-- 3 to 8 ways people ask it -->
    <li>Look up order {order}</li>         <!-- {order} = a slot, filled from the question -->
    <li>Show me order {order}</li>
    <li lang="sw">Nionyeshe oda {order}</li>
  </ul>

  <div class="kb-a">Here is what I found:</div>                 <!-- lead-in; the resolver adds the rows -->
  <p class="kb-denied">You don't have the permission to look up customers' orders.</p>
  <p class="kb-empty">I couldn't find an order with that number.</p>
</article>

The attributes

AttributeRequiredMeaning
idyesUnique, area.topic, never reused. It is the label the NLP is trained to predict later, so renaming one is a breaking change.
data-audienceyesOne or more of guest customer vendor applicant driver staff, or any. Account kinds, not roles.
data-requiresnoPermission keys from the catalogue, all required. Empty means no permission needed. The lint checks every key exists in Catalog::PERMISSIONS.
data-sensitivityyespublic (anyone may read the text), own (about the caller's own account), restricted (needs a permission). Decides whether the text may ever be offered to an outside model (chapter 9).
data-resolvernoName of a server function that fetches live data (chapter 8). The entry's own text is the lead-in.
data-keywordsnoExtra words that should lift this entry. A nudge, never a substitute for good question variants.
data-follownoEntry ids to offer as "you might also ask".
data-statusnoplanned marks text that describes behaviour not shipped yet. The importer refuses planned entries in production.
data-reviewednoDate a named person checked the text. Empty means draft: the production importer refuses it. Every entry in this guide is a draft until the owner signs it off.

The parts inside an entry

.kb-title
Short name. Also used as a matching variant and as the "did you mean…" label.
.kb-q items
The ways people ask. Real phrasings beat clever ones. Mark other languages with lang="sw". Use {order}, {payment}, {customer}, {email} where a reference belongs.
.kb-a
The answer, short enough to read in one glance. Placeholders like {{company.name}} and {{support.email}} are filled from settings at answer time, so nothing is hardcoded.
.kb-more
Optional longer explanation, shown behind "More".
.kb-denied
What to say when the person isn't allowed. Must be safe for anyone to read: it never contains restricted content. Required whenever someone could reach the topic but not see it: an entry with a data-requires, or a customer-only entry a guest might ask about.
.kb-empty
What to say when a resolver finds nothing (or finds something outside the caller's scope: same words either way).

Authoring rules

  1. One question per entry. If an answer starts "it depends", it is two entries.
  2. Write the questions the way people type them, typos aside (the matcher forgives those). Pull real ones from the Mimi query log.
  3. State only what is true for everyone allowed to see the entry. Anything that differs by person, branch or day comes from a resolver, not from prose.
  4. Don't use role names to decide anything. Put the permission in data-requires. Plain-language mentions of a level name such as "administrator" inside an answer are fine; keep them out of the data-* attributes.
  5. No secrets, ever. Entries are readable by design. Keys, passwords and vault contents never live in an entry.
  6. Date it. Setting data-reviewed is the act of taking responsibility for the wording.

7How the local engine answers

No training, no model file, nothing a person can't read. That is deliberate for phase one: when an answer is wrong you can see exactly why.

  1. Normalise. Lower-case, strip accents and punctuation; m-pesa becomes mpesa.
  2. Pull out slots. Order numbers, payment numbers, customer numbers and emails are cut out and replaced by placeholder words (ordref, payref, custref, emailaddr), so "show me order WNKJ-SO-00012" is compared as "show order ordref". The order-number pattern is built from the voucher series prefixes in Books, not hardcoded; that is the fix for gap G5.
  3. Tokenise. Drop filler words; reduce tracking→track, deliveries→delivery; map synonyms to one canonical word (pay, payment, M-Pesa, checkout, lipa all become pay). The synonym list is data, below.
  4. Candidates. Keep only entries visible to this caller (chapter 5).
  5. Score each candidate against each of its question variants and keep the best.
  6. Decide using the thresholds below.
  7. Resolve. If the entry has a resolver, run it. If it needs a slot the question lacked, ask for it ("Which order? Send the number, like WNKJ-SO-00012").
  8. Log the entry id, confidence and who answered.

The scoring, in plain words

coverage = how much of your question this variant explains. precision = how much of the variant your question explains. score = the harmonic mean of the two (so both have to be good), plus up to 0.15 for hitting the entry's keywords.

Each word is weighted by rarity across the entries you may see (IDF), so "the order" counts for less than "refund". A word nobody has written about lowers confidence, which is the right behaviour: the layer should hesitate when it doesn't recognise what you said. A word within one typo (5–7 letters) or two (8+) of a known word counts at 0.7, so "paymnt" still works.

Starting thresholds (to be tuned on the golden set and in shadow mode, not treated as constants)
ScoreOutcome
0.60 and upAnswer. Run the resolver if there is one.
0.45 to 0.60"Did you mean…" with up to three of the person's own visible options as buttons.
Below 0.45No match. Shadow pass for a restricted topic; otherwise the fallback policy.

Two more rules sit on top of the table. Restricted wins when it is clearly better: if an entry the person can't see scores 0.60 or more and beats the best visible one by 0.10 (or nothing visible reaches 0.60), they get that entry's refusal line instead of a weaker visible answer. Near-ties ask instead of guess: if the top two are within 0.04, both are offered as buttons.

Known limit: long, rambling messages score lower, because the extra words are unexplained. That is deliberate (the layer should hesitate rather than guess), and it is the first thing the trained NLP in phase 3 improves. Try pasting a long message as the sales rep in chapter 2.

Languages

Kenyan customers write in English, Swahili and a mix. The first release handles English and Swahili by listing question variants in both (the entries marked lang="sw" are starters for a fluent speaker to review). If most of a question's words are unknown, the engine treats the language as unsupported and hands the question to the fallback, because an outside model is still the better reader of an unfamiliar language.

Synonyms are data

The groups live in one list at the top of the script in this page, and in a database table on the server. Adding "lipa" to the pay group is a data change reviewed like an entry, not a deployment.

Follow-ups ("and the payment?") will use the last matched entry in the session. That is phase 4; the first release treats each message on its own.

8Live data: resolvers

Knowledge entries are text someone wrote. Orders, balances and stock are facts that change. A resolver is a small server function that fetches exactly those facts, for one caller, and hands back a few formatted lines. This is how "where is my order?" is answered locally, with real data, without that data going anywhere.

The contract

// every resolver implements this
interface Resolver {
    public function requires(): array;        // permission keys, re-checked here even if the entry was visible
    public function kinds(): array;           // account kinds allowed: ['customer'] | ['staff'] ...
    public function needs(): array;           // slots it cannot run without: ['ordref'] ...
    public function run(CallerContext $c, array $slots): Result;   // ok(lines, rows) | empty | denied | ask(slot)
}

Rules

  1. Call the same code the screens call. A resolver for orders goes through the same query path, data scope and branch limit as the Orders screen. It does not write its own Voucher::query(); that is how G2 happened.
  2. Allowlist fields. A resolver names the fields it returns. It never serialises a model. If a new column is added to customers tomorrow, nothing leaks until someone deliberately lists it.
  3. Same words for "not found" and "not yours". Otherwise the difference tells a curious person which order numbers exist.
  4. Small answers. At most eight rows. A resolver that returns a table is a report, and reports live on report screens.
  5. Format on the server. The resolver returns finished lines. Nothing downstream ever sees the raw rows.
  6. Log the call, not the content. Store the resolver name and the row count. For own and restricted answers, store the reply with the values blanked, not the values themselves.

The local layer won't know everything. Free-form questions, unfamiliar languages and odd phrasings will still need a language model. The point is that using one becomes a decision with rules rather than the default.

Redaction, in one example

// the person types
"My email is wanjiru@example.com and order WNKJ-SO-00012 hasn't arrived, call 0712 345 678"

// what could leave the server (ai_public)
{
  "system": "You are Mimi, a shop assistant. Use only the snippets. Never ask for passwords or card details.",
  "snippets": ["store.delivery", "mimi.human"],            // P0 entry text only
  "question": "My email is [EMAIL_1] and order [ORDER_1] hasn't arrived, call [PHONE_1]"
}
// the swap table [EMAIL_1] → wanjiru@… never leaves; the reply is re-hydrated here
Redaction is a seatbelt, not the brakes

Patterns catch emails, phones, reference numbers and long digit runs. They cannot catch every name in free text. The primary control is the class gate: P1, P2 and P3 values are never put into the payload in the first place. The redactor is there for what a person types themselves.

Telling people

  • Each reply carries a small label: Answered on our server or AI-assisted. A person should always be able to tell.
  • The Mimi usage policy needs a new major version when this ships. It currently says Mimi is "powered by a large language model" and lists what is logged; the new wording must say common questions are answered locally and when an outside service may be asked. A major version makes everyone re-accept, which is exactly what we want here.
  • Provider choice stays on the AI → Keys screen. If a provider's region matters to you (Qwen's default endpoint is Alibaba's), set used_for and key order accordingly; only fallback traffic reaches them now.

10Guardrails, logs and learning

Guards, in the order they run

  1. Throttle (exists: 10 a minute for guests, 30 for signed-in).
  2. Block check (MimiBlockService, exists).
  3. Consent (MimiPolicyService, exists).
  4. Input limits (exists: 2,000 characters, 20 turns).
  5. Harm scan, now first. MimiHarmScannerService::scan($query, []) is already public and works with an empty provider payload, so the guard can call it before anything else happens. A harmful question is refused, logged with its category, and never reaches matching or an outside model.
A useful side effect

The local layer is not a language model, so it cannot be talked into doing something. Entries and resolvers are code and reviewed text, and "ignore your instructions" matches nothing. Prompt injection only matters on the fallback path, where the user's text is untrusted input and P2 data is never present to be exfiltrated.

What gets logged

The existing mimi_query_logs row gains these columns (sketch in chapter 13):

answered_by

Replies that came from own or restricted resolvers are stored with the values blanked ("2 orders listed"). The people who review flagged questions need the question and the verdict, not another copy of someone's order list.

The learning loop

  1. Every message logs how it was answered.
  2. A Gaps screen (in AI analytics, next to the Mimi screens) lists questions answered by ai or none, grouped by similarity, most frequent first.
  3. Someone holding mimi.knowledge adds the question as a new variant of an existing entry, or writes a new entry.
  4. Saving runs the lint, the leak matrix and the golden set (chapter 11). A failing save is refused.
  5. A second person sets data-reviewed; the entry goes live and its version goes up.
  6. Weekly numbers on the existing Mimi overview: share answered locally, share unanswered, lowest-confidence answers, estimated saving (tokens × AiGateway::RATES).

The same log is, with the redactor applied, the training set for the NLP in chapter 12. Nothing new needs collecting.

12Roadmap to a trained NLP

  1. 0

    Structured knowledge this guide

    Entry format, caller context, resolver contract, fallback policy and a working prototype.

    Done when: the owner has read chapters 3, 5 and 9 and decided the fallback defaults; the entries have been reviewed.

  2. 1

    Server engine v1: no training

    Importer, caller context, guard-first, matcher, three public resolvers, answered_by logging, Off · Shadow · On.

    Done when (suggested): in Shadow mode, the layer answers a clear majority of the questions people actually ask, and where it and today's reply disagree, a reviewer sides with the local one.

  3. 2

    Roles, resolvers and the leash

    Permissioned resolvers for orders, customers and payments; fallback modes with the redactor; the policy's new major version; the entry editor and Gaps screens.

    Done when: the leak matrix and the fallback egress test run in CI, and G2 is closed.

  4. 3

    Train the NLP

    Learn from the log what keywords can't see. See the options below.

    Done when: the model beats phase 1's matcher on a held-out set and the golden set, and the leak matrix still passes.

  5. 4

    Conversation and language

    Follow-ups ("and the payment?"), better Swahili and mixed-language questions, vendor, applicant and driver audiences, optional thumbs up/down.

Rules for whatever is chosen

  1. The model proposes; the permission filter disposes. The classifier only ever scores entries the caller may see (mask them before the argmax), so no model can resurrect a hidden entry.
  2. Train on redacted text only, from the log, excluding flagged-harmful questions. Labels come from the entry a person confirmed on the Gaps screen.
  3. Version the model with the entries. Entry ids are the class names, which is why ids are never reused.
  4. Ship only if it wins. Hold out 20%, compare against the phase 1 matcher, and re-run the leak matrix.
  5. Training is offline. A script on a developer machine produces a file; the live server never trains.

Clearance levels

  • What are the clearance levels?
  • What does clearance mean?
  • What is clearance level 3?
  • Who can manage whom?
  • What is a clearance?

Clearance is a number from 0 to 6. It is a ceiling and an authority, not a permission: it decides which roles someone may hold and whom they may manage (only people strictly below their own level). Roles are what actually grant permissions.

  • 0 No staff access: customers, vendors, applicants
  • 1 Staff: a defined job at a branch
  • 2 Officer: runs a function
  • 3 Manager
  • 4 Senior: sees across every branch for their field
  • 5 Administrator
  • 6 Owner

The level names can be renamed under Settings, Roles & access.

Branch limits

  • What are branch limits?
  • Why can't I see another branch's vouchers?
  • What is branch scope?
  • What does test mode do?
  • Why do I only see my branch?

Branch limits keep a person to the branches they've been given. For Books (vouchers, day book, reports) and Stock (transfers, counts, jobs, expiry) the owner sets each area to Off, Test or On.

  • Test allows everything but records what would have been hidden or refused.
  • On enforces it: you see and post only for your branches. A view-only grant lets you look but not post.

People whose role covers every branch are never limited, and records with no branch stay visible to everyone.

It is set under Settings, Roles & access, Branch limits.

Giving someone a role

  • How do I give someone a role?
  • Who can make an admin?
  • Can I change my own role?
  • Who can assign roles?

Roles are given on Settings, Roles & access, People, by someone who holds access.manage. The rules:

  • You can only give roles, and clearance, strictly below your own clearance.
  • Only the owner can make administrators or build new roles.
  • You can't change your own role (the owner is the exception), and the last owner can't be lowered or removed.
  • Every change is written to the access log.

How money moves in the books

  • How does a voucher post?
  • Why must a voucher balance?
  • What is a control ledger?
  • How do I reconcile registers?
  • Where is reconciliation?

Money only moves through vouchers (sales, receipts, payments, journals…). Every voucher balances: total debits equal total credits, in the voucher's currency and in the base currency.

Registers are detail, never money: gift voucher codes, loyalty point lots, withholding certificates and bill references explain a ledger balance but never replace it. Each register reconciles to a control ledger. See Books → Reports → Reconciliation.

The full explanation is the Ledger guide (docs/LEDGER_GUIDE.md).

15FAQ and glossary

Does this replace Gemini, Claude or OpenAI?
No. They stay behind AiGateway, with the same keys, order and failover. They change from the only brain to the fallback, with a leash.
Is this "AI" if nothing is trained?
Today it is retrieval and rules: a transparent matcher over reviewed text and permissioned data. That is a feature for phase one, because every answer can be explained. The trained NLP in chapter 12 improves recall; it doesn't change who is allowed to see what.
Why not just filter the prompt we send now?
Filtering a prompt is a blacklist: one forgotten field leaks. Here, P1 to P3 data is never fetched for the outside route at all, so there is nothing to forget. It is also cheaper, because most questions never make the trip.
What if two entries match almost equally?
The higher score wins. If the top two are within 0.04 of each other, the person gets both as "did you mean…" buttons instead of a guess.
Where do prices and stock levels go?
Never in prose. They change, so they come from a resolver (catalogue.public), formatted at answer time.
What if an entry is wrong?
Every answer logs the entry id, so a wrong one is traceable in one click. Fix the entry once and it is fixed for everyone; the version goes up and the old text is kept.
Does this page send my questions anywhere?
No. It has no network code, loads no outside fonts or scripts, and counts any fetch, XHR or beacon it makes (the meter in chapter 2 stays at 0). You can also watch the Network tab in your browser's developer tools.

Glossary

Caller context
The account kind, permissions, data scope, branches and language of whoever is asking, built on the server.
Entry
One article.kb: one question, its variants, its answer, and who may see it.
Variant
One way of asking an entry's question.
Slot
A reference cut out of the question (order, payment or customer number, email) and passed to a resolver.
Resolver
A permissioned server function that fetches live data for one caller and returns a few finished lines.
Confidence
The matcher's score from 0 to 1 for an entry against a question.
Data class
P0 public, P1 own, P2 restricted, P3 never. Decides what may reach an outside model.
Fallback
What happens when the local layer isn't confident: stay local, or ask an outside AI under the owner's rules.
Shadow mode
The local layer computes and logs its answer while the person still gets today's reply, so you can compare safely.
Golden set
A fixed list of questions with the entry each should reach, run on every change.
Egress
Anything that leaves our server for another party.
