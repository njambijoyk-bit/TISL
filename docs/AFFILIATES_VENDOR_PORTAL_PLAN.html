1. What exists today

User & role architecture

  • Authorizer engine (Services/Access/Authorizer.php) with clearance levels 0–6 and a role builder that produces per-company roles.
  • Portal accounts (customer, vendor, applicant) sit at clearance 0, hold no permissions, and see only their own data.
  • Staff accounts (super_admin through driver) hold granular permissions from the Catalog.
  • Frontend uses access.account and hasPermission() — never compares role names.

Vendors Exists

  • Vendor model with user_id for portal login
  • Admin CRUD at /admin/vendors
  • Statuses: active, pending_approval, suspended
  • Login works via the standard /login endpoint
  • No self-registration
  • No portal pages

Referrals Exists

  • ReferralCode model: code, reward tracking, conversion dates
  • Tied to customer_id only
  • ReferralCodeUsage tracks each use
  • Customer gets a personal referral code on registration
  • Not available to vendors

Extras module Exists

Already lives in the Catalog under permissions: pos.*, hr.*, driver.app, algorithm.*, analytics.view, engagement.*. Affiliates will sit here as a new permission group.

2. Affiliates in the Extras module

The core idea: any customer or vendor can become an affiliate — they get a unique referral code, a dashboard showing their referrals and commissions, and payouts tracked through the books.

Data model changes Backend

New: affiliates table

A first-class affiliate profile linked to a user, independent of customer/vendor.

affiliates
├── id
├── user_id          → users.id (unique)
├── affiliate_code   → unique, e.g. AFF-XXXX
├── affiliate_type   → 'customer' | 'vendor'
├── commission_rate  → decimal (override, nullable)
├── tier             → 'standard' | 'silver' | 'gold'
├── status           → 'active' | 'suspended' | 'pending'
├── approved_at
├── total_referrals  → cached counter
├── total_earnings   → cached monetary total
├── metadata         → JSON (extra config per company)
└── timestamps

Extend: referral_codes table Extend

+ affiliate_id   → affiliates.id (nullable, alongside customer_id)
+ source_type    → 'customer' | 'affiliate'
+ campaign       → string, nullable (group codes by campaign)

New: affiliate_referrals table

Tracks every referral event with its outcome and commission.

affiliate_referrals
├── id
├── affiliate_id     → affiliates.id
├── referred_user_id → users.id
├── referral_code_id → referral_codes.id
├── event_type       → 'signup' | 'first_order' | 'subscription'
├── status           → 'pending' | 'qualified' | 'paid' | 'rejected'
├── commission_amount
├── qualified_at
├── paid_at
└── timestamps

New: affiliate_payouts table

affiliate_payouts
├── id
├── affiliate_id     → affiliates.id
├── amount
├── period_start / period_end
├── status           → 'pending' | 'approved' | 'paid'
├── ledger_entry_id  → links to books
├── paid_at
└── timestamps

Backend services Backend

AffiliateService (new)

  • enroll(User) — creates the affiliate profile + referral code, validates user has customer or vendor profile
  • recordReferral(code, newUser) — called from registration, creates affiliate_referrals row
  • qualify(referral) — moves referral to qualified after qualifying event (first order, etc.)
  • calculatePayout(affiliate, period) — tallies qualified referrals × commission rate
  • approvePayout(payout) — staff approves, links to ledger via LedgerService

Registration flow change Extend

The existing AuthController::register() already accepts a referral_code param for customers. Extend it:

User registers → Has referral_code? → Look up in referral_codes → Check source_type → Record affiliate_referral

This hooks the affiliate tracking into both customer and vendor registration (once vendor registration exists).

Frontend: affiliate portal pages Frontend

  • /portal/affiliates — dashboard with stats (total referrals, earnings, conversion rate)
  • /portal/affiliates/referrals — table of referred users + status
  • /portal/affiliates/payouts — payout history & pending
  • /portal/affiliates/enroll — enrollment page (terms, submit)
  • /admin/extras/affiliates — staff management view (list, approve, payouts)

3. Vendor login & registration

Vendors can already log in through the standard /login endpoint, but there is no self-registration and no portal pages. This section adds both.

Vendor self-registration New Backend

New endpoint: POST /register/vendor

In AuthController, alongside the existing customer register():

registerVendor(Request $request)
├── Validate: name, email, password, company_name,
│   contact_name, phone, tax_id (optional),
│   referral_code (optional)
├── Create User with role = 'vendor'
├── Create Vendor profile
│   ├── status = 'pending_approval'
│   ├── Generate vendor_number (VEND-YYYY-NNNN)
│   └── No ledger yet (created on approval)
├── If referral_code → AffiliateService::recordReferral()
├── Fire VendorRegistered event
│   └── Notify admins (staff with vendors.approve)
└── Return token + access summary
   (login works immediately, but portal
    shows "pending approval" state)

Approval flow

Vendor registers → pending_approval → Admin reviews → Approved → Ledger created

On approval, VendorController::approve() sets status = 'active' and calls LedgerService::vendorLedger() to create the Sundry Creditors entry. Vendors with pending_approval can log in and see their profile but cannot transact.

Vendor portal pages New Frontend

Registration page

/register/vendor — separate from the customer registration. Fields: company name, contact name, email, phone, password, tax ID (optional), referral code (optional).

Portal pages (behind account:vendor)

RoutePage
/portal/vendor/dashboardOverview: status, profile completion, recent POs
/portal/vendor/profileEdit company details, bank info, tax ID

Frontend routing (App.jsx)

Add a <Route path="/portal/vendor/*"> block guarded by isVendor(), mirroring the existing customer portal pattern. The login page stays shared — after login, the app redirects based on access.account.

Backend routes Backend

// routes/api.php — new vendor portal group
Route::prefix('portal/vendor')
  ->middleware(['auth:sanctum', 'account:vendor'])
  ->group(function () {
    Route::get('dashboard', [VendorPortalController::class, 'dashboard']);
    Route::get('profile',   [VendorPortalController::class, 'profile']);
    Route::put('profile',   [VendorPortalController::class, 'updateProfile']);
    Route::get('orders',    [VendorPortalController::class, 'orders']);
    Route::get('products',  [VendorPortalController::class, 'products']);
    Route::get('invoices',  [VendorPortalController::class, 'invoices']);
    Route::get('statements',[VendorPortalController::class, 'statements']);
  });

A new VendorPortalController serves the vendor's own data, scoped to their vendor_id. Separate from the existing admin VendorController.

Portal-side: no permission changes

Affiliates who are customers/vendors still hold no permissions (clearance 0). Their affiliate dashboard is a portal page gated by account:customer or account:vendor middleware plus a check that an affiliates record exists. The Authorizer doesn't need to change.

Frontend role helpers Frontend

Add to _shared/lib/roles.js:

export const canViewAffiliates = (user) =>
  hasPermission(user, 'affiliates.view');
export const canManageAffiliates = (user) =>
  hasPermission(user, 'affiliates.manage');
export const canApproveVendors = (user) =>
  hasPermission(user, 'vendors.approve');

The access summary from /me already includes account type, so isVendor() and isCustomer() work unchanged. Add an affiliate flag to the summary when the user has an affiliate profile:

// Authorizer::summary() addition
'affiliate' => $user->affiliate?->status === 'active'

6. Migration & schema reference

New migrations (in order)

1. create_affiliates_table
   └── After: existing users + vendors tables

2. add_affiliate_columns_to_referral_codes
   └── Adds: affiliate_id, source_type, campaign
   └── After: affiliates table exists

3. create_affiliate_referrals_table
   └── After: affiliates + referral_codes

4. create_affiliate_payouts_table
   └── After: affiliates table

Existing tables touched

TableChange
referral_codesAdd affiliate_id, source_type, campaign
usersNo changes needed
vendorsNo changes needed (already has user_id, status)

Key relationships

User ──┬── Customer ──── Affiliate (via user_id)
       │                    ├── ReferralCodes
       │                    ├── AffiliateReferrals
       │                    └── AffiliatePayouts
       │
       └── Vendor ────── Affiliate (via user_id)
                            ├── ReferralCodes
                            ├── AffiliateReferrals
                            └── AffiliatePayouts

The Affiliate model ties to User (not to Customer or Vendor directly). The affiliate_type column records which portal type they are, but the foreign key is user_id. This keeps the model simple and lets the same affiliate system work for future portal types.
