1. What exists today

User & role architecture

  • Authorizer engine (Services/Access/Authorizer.php) with clearance levels 0–6 and a role builder that produces per-company roles.
  • Portal accounts (customer, vendor, applicant) sit at clearance 0, hold no permissions, and see only their own data.
  • Staff accounts (super_admin through driver) hold granular permissions from the Catalog.
  • Frontend uses access.account and hasPermission() — never compares role names.

Vendors Exists

  • Vendor model with user_id for portal login
  • Admin CRUD at /admin/vendors
  • Statuses: active, pending_approval, suspended
  • Login works via the standard /login endpoint
  • No self-registration
  • No portal pages

Referrals Exists

  • ReferralCode model: code, reward tracking, conversion dates
  • Tied to customer_id only
  • ReferralCodeUsage tracks each use
  • Customer gets a personal referral code on registration
  • Not available to vendors

Extras module Exists

Already lives in the Catalog under permissions: pos.*, hr.*, driver.app, algorithm.*, analytics.view, engagement.*. Affiliates will sit here as a new permission group.

2. Architecture decisions

Core vs Extras: what lives where

The vendor ledger (Sundry Creditors) is a books concept and stays in Core. It already works: VendorController creates a vendor + ledger, purchases post against it, nothing changes. The new vendor-facing features — portal login, self-registration, tendering, pre-qualification, and affiliates — all live in the Extras module and are only available when Extras is licensed and switched on.

FeatureModuleGate
Vendor model + admin CRUDCorePermissions: vendors.view, vendors.manage
Sundry Creditors ledgerCoreCreated on vendor store (admin) or on approval (self-reg)
Vendor orders (renamed PO model)CorePermissions: vendors.view
Vendor self-registration + portal loginExtrasmiddleware('module:extras')
Vendor portal pages (dashboard, profile, orders, invoices)Extrasmiddleware('module:extras', 'account:vendor')
Tendering + bidsExtrasmiddleware('module:extras') + permissions
Pre-qualificationExtrasmiddleware('module:extras') + permissions
AffiliatesExtrasmiddleware('module:extras') + permissions

The EnsureModuleActive middleware already returns 404 when a module is not licensed/on, so the pattern is established. The frontend uses isModuleActive('extras') to hide nav links and routes.

Rename: PurchaseOrder → VendorOrder

The existing PurchaseOrder model causes confusion with the books purchase_order voucher type (a completely separate concept). Rename it to reduce ambiguity:

What changes

  • Vendor.php — relationships purchaseOrders() renamed to vendorOrders(), openPurchaseOrders() → openVendorOrders(), column total_purchase_orders → total_vendor_orders
  • ModuleTables.php — backup table list updated
  • Migration: rename_purchase_orders_to_vendor_orders (renames both tables + FK columns)
  • Frontend vendor API updated to match new endpoint names

What does NOT change

  • The books VoucherType::PURCHASE_ORDER ('purchase_order') and its voucher flows — that is a financial document, not this model
  • DashboardService, CostCentreService — they reference the voucher base type string 'purchase_order', not the model
  • Preorder supply — references purchase_order voucher type strings, not the PO model

Route structure

How the backend routes split between Core and Extras:

// Core (always available) — existing, no change
Route::middleware('permission:vendors.view')
  ->prefix('admin/vendors')->group(...)       // Admin CRUD + ledger

// Extras (gated) — all new
Route::middleware('module:extras')->group(function () {

  // Public (no auth): vendor self-registration
  Route::post('register/vendor', ...);

  // Vendor portal (auth + account type)
  Route::middleware(['auth:sanctum', 'account:vendor'])
    ->prefix('portal/vendor')->group(...)    // dashboard, profile, orders...

  // Vendor portal: tendering + PQ
  Route::prefix('portal/vendor')->group(function () {
    Route::get('tenders', ...);              // browse open tenders
    Route::post('tenders/{id}/bid', ...);    // submit bid
    Route::resource('prequalifications', ...);
  });

  // Admin: tender + PQ management
  Route::middleware('permission:tenders.view')
    ->prefix('admin/procurement')->group(...);

  // Admin: affiliate management
  Route::middleware('permission:affiliates.view')
    ->prefix('admin/extras/affiliates')->group(...);

  // Portal: affiliate dashboard (customer OR vendor)
  Route::middleware('auth:sanctum')
    ->prefix('portal/affiliates')->group(...);
});

The core idea: any customer or vendor can become an affiliate — they get a unique referral code, a dashboard showing their referrals and commissions, and payouts tracked through the books.

4. Vendor login & registration

Vendors can already log in through the standard /login endpoint, but there is no self-registration and no portal pages. This section adds both.

Vendor self-registration New Backend

New endpoint: POST /register/vendor

In AuthController, alongside the existing customer register():

registerVendor(Request $request)
├── Validate: name, email, password, company_name,
│   contact_name, phone, tax_id (optional),
│   referral_code (optional)
├── Create User with role = 'vendor'
├── Create Vendor profile
│   ├── status = 'pending_approval'
│   ├── Generate vendor_number (VEND-YYYY-NNNN)
│   └── No ledger yet (created on approval)
├── If referral_code → AffiliateService::recordReferral()
├── Fire VendorRegistered event
│   └── Notify admins (staff with vendors.approve)
└── Return token + access summary
   (login works immediately, but portal
    shows "pending approval" state)

Approval flow

Vendor registers → pending_approval → Admin reviews → Approved → Ledger created

On approval, VendorController::approve() sets status = 'active' and calls LedgerService::vendorLedger() to create the Sundry Creditors entry. Vendors with pending_approval can log in and see their profile but cannot transact.

5. Tendering system

Staff post a tender (request for proposal/quotation), approved vendors see it in their portal, and submit bids. Staff evaluate, score and award. The flow mirrors how purchase orders already work but adds a competitive bidding layer before a PO is raised.

Tender lifecycle

Staff creates tender → Published → Vendors submit bids → Bidding closes → Evaluation → Awarded → PO raised

6. Vendor pre-qualification

Before vendors can bid on certain tenders, they fill out a pre-qualification document. Staff configure which sections/questions appear, vendors submit with supporting documents, and staff evaluate. A qualified vendor gets a category and expiry date. This mirrors the Application/ApplicationDocument pattern from the careers module.

How it works

Staff builds PQ template → Vendor fills form → Uploads documents → Staff reviews → Qualified / Rejected

Qualified vendors can bid on tenders with visibility = 'prequalified'. Qualification is per category and expires, so vendors re-qualify periodically.

Data model Backend

New: prequalification_templates table

Staff define what the PQ form asks. Multiple templates for different categories.

prequalification_templates
├── id
├── name                → e.g. "General Supplies PQ"
├── category            → 'goods' | 'services' | 'works'
├── description
├── sections            → JSON [{title, description, fields: [
│                            {key, label, type, required, options}
│                          ]}]
│                          types: text, textarea, number, select,
│                          checkbox, file, date
├── required_documents  → JSON ['tax_compliance', 'registration',
│                          'insurance', 'financial_statement',
│                          'reference_letter', 'other']
├── validity_months     → how long a qualification lasts
├── is_active           → boolean
├── created_by
└── timestamps

│                           'insurance' | 'financial_statement' |
│                           'reference_letter' | 'bank_reference' |

├── verified_by / verified_at

Linking to tenders

When a tender has visibility = 'prequalified', the system checks:

Vendor can bid IF:
  prequalifications.vendor_id = vendor.id
  AND status = 'qualified'
  AND expires_at > now()
  AND categories_qualified includes tender.category

  • review(prequalification, staff, score, notes) — staff evaluates
  • qualify(prequalification, categories) — sets qualified status + expiry date
  • reject(prequalification, reason) — with reason, vendor can reapply
  • checkExpiry() — scheduled job: expires qualifications past their date, notifies vendors to reapply
  • isQualified(vendor, category) — quick check for tender eligibility
